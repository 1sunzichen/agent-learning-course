1-4|跨会话记忆|把值得保留的信息写入向量库，下次用问题检索回来。|程序重启后，普通 messages 列表会丢失；持久化让过去的信息还能参与回答。|只取相关记忆，避免把所有历史都塞进提示词。|相似度不等于事实正确；需要处理过期记忆、重复数据和用户隔离。|需要记住用户长期偏好的助手。|一次性问答，或没有权限保存个人信息的服务。|记住“我喜欢清淡”，换一种问法询问饮食偏好，观察 recall 是否找到原记录。
1-5|流式输出与工具调用|逐段接收模型输出；工具参数收齐后再调用工具，把结果交回模型。|整段生成完才显示会让用户一直等待，而工具参数又可能被切成多段。|用户更早看到文字；能理解文字流和工具调用如何衔接。|分片组装、多个工具索引和中途断流增加处理难度；流式不保证总耗时更短。|聊天界面、需要即时反馈的问答。|只需要最终结构化结果的后台批处理。|观察一个工具参数是否分多次到达：参数完整前能否解析 JSON？
1-6|先计划再执行|先生成步骤，再让执行器按步骤调用工具并汇总。|复杂问题一次直接回答容易漏步骤；拆开后能检查每步是否完成。|计划可见，失败时容易定位到具体步骤。|计划可能一开始就错；计划器和执行器增加调用成本。|依赖顺序明确的查询、比较和计算任务。|一句话就能回答的问题，或环境变化太快却没有重新规划能力的任务。|删掉计划中的一个必要步骤，观察执行器能否发现结果缺失。
1-7|反思与修订|先回答，再让模型检查答案，最后根据检查意见修订。|第一版可能遗漏约束；独立一轮检查有机会补上。|把检查意见保留下来，便于比较修改前后。|同一个模型可能重复自己的错误；多一轮反思不等于验证为真。|可以用明确条件检查的草稿、解释或解题过程。|必须由真实数据或确定性测试保证正确的关键判断。|给答案加一个可检查的限制，比较反思是否指出违反之处。
1-8|工具超时与重试|给天气工具增加失败重试、超时处理和结果缓存。|外部请求会失败或重复发生，不能让一次偶发错误终止整个流程。|临时故障可恢复，相同查询命中缓存时减少重复请求。|重试增加延迟；按城市缓存会过期。缓存查询结果不等于保证写操作幂等。|只读查询、可以安全重复的工具。|扣款、发信等有副作用的操作，除非另有业务幂等机制。|让第一次请求失败，检查重试次数；再查同城，检查缓存是否省去请求。
1-9|单 Agent 调用记录|把模型和工具执行过程记下来，展示调用与耗时。|只看最终答案无法知道慢在哪、错在哪。|可以沿记录回看输入、输出和执行步骤。|进程内记录不是完整监控系统；真实日志还需脱敏、存储和查询。|调试工具调用链、比较不同实现耗时。|需要跨进程追踪和长期审计却只有内存日志的系统。|让某个工具变慢，检查能否从记录中定位这一段。
1-10|完整单 Agent|把工具分发、错误处理和记录接入同一个模型循环。|单个机制学会后，需要看到它们如何共同服务一次用户请求。|一个入口能串起模型决策、执行工具和返回答案。|循环控制更复杂，工具出错和模型反复调用都需要上限与诊断。|小型有工具的问答助手原型。|直接承担高风险写操作的生产系统。|给一个需要天气和计算的问题，追踪两次工具结果怎样回到模型。
1-11|上下文窗口管理|估算历史长度，超出阈值时压缩历史并保留近期消息。|模型输入长度有限，历史越来越长还会增加延迟和费用。|持续对话不必无限保留所有原文。|字符估算不是精确 token 数；摘要会丢失细节。|长对话、保留大意比保留逐字原文更重要的场景。|需要逐条原文追溯的记录系统。|在早期消息埋入一个数字，触发压缩后检查数字是否仍被保留。
1-12|Token 与费用估算|按输入和输出用量分别计算费用，并与估算比较。|只看调用次数无法解释成本：每次输入输出长度都不同。|费用公式透明，便于比较提示词和回答长度。|源码单价是示例配置，不代表当前价格；估算应与供应商实际 usage 对照。|预算教学、不同方案的成本比较。|直接用字符估算作为正式账单。|把历史长度加倍，比较输入费用如何变化。
1-13|提示词策略对比|对同类问题尝试直接提问、示例、分步提示和角色提示。|提示内容改变模型收到的任务约束，需要通过对照看效果。|修改成本低，能快速比较表达方式。|单次好结果可能是偶然；更长提示增加成本，也可能限制过头。|有固定评价标准的提示词实验。|没有测试集却宣称某种提示永远更好。|用同一组问题比较四种提示，并记录正确率和输出长度。
1-14|结构化结果|让模型输出 JSON，解析失败时反馈错误并重试。|程序需要可靠字段，不能只接收一段自由文本。|结果可以进入后续函数和数据存储。|合法 JSON 不代表字段完整或内容正确；仍需类型和业务校验。|信息抽取、表单填充、机器间传值。|仅凭能解析就执行敏感操作。|让输入缺少一个字段，检查结果是明确空值还是模型编造。
1-15|请求缓存|相同请求再次出现时优先返回已保存的响应。|重复询问若每次调用模型，会重复付费和等待。|命中时速度快、减少调用费用。|缓存键需要考虑模型、提示词与用户；内存缓存重启即丢失，过期策略另需设计。|重复率高、答案变化慢的只读问答。|实时行情或不能混用不同用户答案的业务。|连续问两次，再改一个字符，观察是否命中及耗时差异。
1-16|提示注入实验|比较直接拼接不可信文本与加入防护后的行为。|文档或用户文本可能夹带“忽略规则”等指令，干扰原任务。|能直观看到提示边界的重要性。|关键词过滤和系统提示都不是完整安全边界，绕过形式很多。|在无副作用环境里学习和测试提示注入。|把这段示例当作工具权限、数据隔离或授权的替代品。|换一种不含原关键词的攻击表达，观察防护是否仍有效。
1-17|对话状态机|根据当前状态收集信息，并在条件满足后转到下一步。|自由对话容易跳过必要字段；状态把流程约束显式化。|每一阶段的必填信息和出口容易检查。|状态和分支变多后维护成本上升；模型抽取失败需要回退路径。|预约、下单前的信息收集。|完全开放、无法定义阶段的自由聊天。|在收集第二个字段时修改第一个字段，观察状态是否正确更新。
1-18|异步工具并行|对比逐个等待与同时等待多个天气任务。|相互独立的等待时间可以重叠，不必排队相加。|等待型任务可降低总耗时。|共享资源、异常传播和并发上限更复杂；模拟 sleep 的收益不代表真实系统。|相互独立的网络或磁盘查询。|有前后依赖的任务，或纯 CPU 重计算。|把一个工具等待时间调长，对比串行与并行的总时长。
1-19|单 Agent 评测|用固定问题集运行 Agent，再判定答案是否满足期望。|凭聊天感觉难以判断改动是否真的提升质量。|同一测试集可重复比较版本。|样本少会偏；模型裁判可能误判，要保留人工核对样本。|提示词或模型改动后的回归比较。|少量样例全部通过就声称对所有问题可靠。|加入一个容易误判的同义表达，比较精确匹配和裁判结果。
2-1|调度者与执行者|调度者拆任务，执行者分头处理，最后汇总。|不同子任务有不同目标，把职责分开便于控制。|拆解和汇总各自清楚，便于替换某个执行者。|调度者可能成为瓶颈，拆错任务会影响全链路。|能分解为几个专业子任务的报告或分析。|简单请求，或子任务之间需要密集交互却没有共享机制。|让一个执行者只返回部分信息，检查汇总是否说明缺失。
2-2|多阶段流水线|研究结果交给写作，写作结果再交给审阅。|后一步需要前一步产物，顺序传递比同时开工更合适。|每阶段输入输出明确，容易单独调试。|早期错误会被后面继承；总延迟累加。|资料整理、成稿、审核等顺序工作。|各任务互相独立且追求并发速度的场景。|故意让研究结果缺少依据，检查审阅能否指出。
2-3|协作讨论|多个角色轮流交换意见，满足共识条件或轮数上限后停止。|单一视角可能遗漏问题，交叉讨论增加检查角度。|意见分歧可见，有机会改进初稿。|达成共识不代表事实正确；讨论可能重复、成本不断增长。|方案审阅、观点比较。|必须有外部证据支撑却只靠模型互相同意的判断。|让两方坚持不同结论，检查轮数上限是否终止讨论。
2-4|竞争与裁判|多个候选独立作答，裁判比较并选择。|同一模型的一次答案可能不是最合适的，多个候选提供选择空间。|候选可并列检查，容易做不同风格实验。|增加生成与裁判成本；裁判也可能偏好文风而非正确性。|文案候选、受明确标准约束的方案选择。|没有评价标准、或预算只容许一次调用的任务。|交换候选展示顺序，观察裁判选择是否稳定。
2-5|Agent 消息信封|给消息附上发送者、接收者、任务标识等字段并检查格式。|多个角色通信需要知道“谁给谁、属于哪件事”。|字段明确，方便路由和追踪。|自定义 JSON 演示不等于完整 A2A 标准实现；没有自动提供网络传输、认证和重试。|学习消息格式、设计内部消息约定。|直接声称能与任意 A2A 服务互通。|删除一个必填字段，观察验证是否拒绝消息。
2-6|共享状态|多个 worker 通过共享字典读写中间结果。|后一个角色需要前一个角色的结果，不应重复计算或丢失上下文。|数据汇聚在一个地方，容易观察变化。|锁只能保护读写，不自动保证业务依赖顺序；共享状态会增加耦合。|单进程、明确写入顺序的小型协作。|跨机器共享或复杂并发一致性需求。|调换两个 worker 的执行顺序，观察读取是否得到缺失值。
2-7|失败降级|优先执行主方案，失败后尝试备用方案。|单个执行者不可用时，仍希望给出可接受的部分服务。|失败不会立即拖垮全部请求。|备用方案质量可能更低；若失败原因相同，反复切换也无效。|允许质量降低的只读查询。|不能重复执行的写操作，或不能接受降级结果的任务。|让主方案失败，再让备用也失败，检查最后如何结束。
2-8|并发数量控制|用信号量限制同时执行的 worker 数量。|一次启动过多请求会占满连接或触发服务限制。|并发度可调，避免无限制拥挤。|限制同时运行数量不等于限制每秒请求数；慢任务会长期占用名额。|大量独立的等待型子任务。|供应商要求严格 QPS 限制却没有额外速率控制的情况。|把上限改为 1 和 3，记录同时运行数量与总耗时。
2-10|多 Agent 综合流程|组合并发 worker、失败处理和结果汇总。|分工只有在失败、等待和汇总都被处理后才能形成完整流程。|一个请求能协调多个执行者，便于比较单 Agent 与多 Agent。|部分失败时结果含义复杂；需要区分失败文本和有效答案。|多个独立分析维度的综合报告原型。|任何一个子结果错误都会导致不可接受后果的直接自动执行。|让一个 worker 抛错，检查其他任务是否继续，以及汇总是否暴露失败。
2-11|任务分解与路由|把文本拆成子任务，按关键词选择匹配的 Agent 执行。|不同任务需要交给不同能力，先做路由才能委派。|规则简单可解释，能看到每项任务被谁接走。|关键词覆盖有限，同义词和多意图容易选错；演示执行者不等于真实模型。|固定领域的教学路由或小型规则分发。|开放领域、表达变化很大的复杂需求。|换掉路由关键词，观察没有执行者认领时返回什么。
2-12|事件总线|订阅者按主题注册回调，发布时找到该主题的订阅者并投递。|发布者不必知道所有接收者，只需要知道消息主题。|发送端和接收端更容易独立扩展。|内存总线没有消息持久化、可靠重投和跨进程能力；同步回调还可能阻塞发布者。|单进程事件通知、理解发布订阅。|要求可靠送达的跨服务消息系统。|发布一个无人订阅的主题，再让两个回调订阅同一主题，观察投递次数。
2-13|黑板协作|所有角色读写同一块黑板，逐步补齐最终建议所需的信息。|角色不必两两传消息，可以从公共状态发现已有资料。|中间结果集中、方便检查与复用。|字段约定和执行顺序隐含依赖；并发写入、过期信息需额外管理。|多个步骤补齐一个结构化结果。|严格隔离数据、或无共同状态结构的任务。|先执行依赖天气的推荐者，检查缺失天气时输出是否合理。
2-14|死锁与重复循环检测|在等待关系中找环，并检测状态重复或步数过多。|Agent 可能互相等待，也可能一直重复同样的动作而不结束。|把“卡住”变成可检测条件，便于终止和诊断。|重复状态不总是错误；图检测成立依赖等待关系建模是否准确。|工作流调试、给迭代过程增加停止条件。|把检测到等待图环直接等同所有运行时死锁而不检查锁语义。|构造 A 等 B、B 等 A，再构造正常链条，比较检测结果。
2-15|跨角色调用链|给一次请求和每段调用生成标识，再按父子关系还原树。|多个执行者的日志混在一起时，需要知道哪些记录属于同一请求。|能看清调用归属和上下游关系。|本地树形演示不包含跨服务上下文传播、采样与集中存储。|理解 trace/span 和调试多步调用。|直接替代完整分布式可观测平台。|让同一角色被两个父节点调用，检查是否能按 parent 区分。
2-16|预算分摊|按每个 Agent 的输入输出用量累计费用，并与预算比较。|总费用高时需要知道花在谁身上，以及何时该停止。|费用可归因，便于调整调用策略。|示例 token 与单价不代表实际账单；调用后记账可能超过预算。|预算教学、离线成本模型。|要求严格绝不超额却没有调用前预留和并发控制的系统。|设置小于一次调用成本的预算，观察何时停止、是否已超额。
2-17|人工确认节点|识别关键步骤，在真正执行前取得人工批准，拒绝时停止或跳过。|发信、改库等动作需要由人承担最终决策，不能只靠模型决定。|关键决策可以插入可见的人工关口。|模拟回复不等于真实审批；审批若放在执行后就无法阻止动作。|学习审批状态和恢复流程。|照搬模拟批准代码直接执行外部副作用。|给关键步骤返回 reject，确认 run_step 是否仍被调用。
2-18|多 Agent 协作评测|计算完成率、协作轮数对应的效率分和产出质量，再加权比较。|仅看最终答案无法体现协作成本和任务遗漏。|可以把多个评价维度放在一起比较。|权重是人为选择；少轮数不必然高质量，样例质量分也不是自动验证。|架构对照实验、固定任务集的趋势比较。|把单个综合分当作所有场景的绝对优劣。|交换效率和质量的权重，观察排名是否变化。
2-19|工具权限与审计|按 Agent 角色检查工具白名单，再检查额外授权并记录结果。|模型说要调用不代表它有权限执行，执行入口需要独立校验。|权限规则集中，拒绝原因可以追踪。|字典里的角色和布尔授权不是可信身份系统；需要阻止绕过检查直接调工具。|演示最小权限、规划工具网关。|将调用方自报身份直接当作生产授权。|用只读角色请求写工具，检查是否在工具执行前拒绝并记录。
3-1|框架工具调用 Agent|把天气与计算工具交给 Agent，模型选择工具，框架或循环执行并回传结果。|手写循环要处理工具描述、参数和消息回填，框架可以统一这些环节。|更容易增减工具和复用调用协议。|框架增加版本依赖和调试层次；工具本身的正确性仍需自己负责。|工具数量逐渐增加的助手原型。|极简规则流程，或必须精确控制每一个调用细节且不愿引入框架的项目。|给出同时需要天气和算术的问题，检查工具结果是否都进入最终回答。
3-2|图式工作流|用节点表示计划、执行与汇总，用边规定下一步。|流程复杂后，显式图比散落的条件判断更容易检查。|阶段与连接关系清晰，节点可以单独替换。|图本身不会自动并行；状态字段和边的错误仍会传播。|阶段固定、需要观察状态变化的任务。|简单直线脚本且没有图管理需求。|去掉通向汇总节点的一条边，思考图在哪里终止。
3-3|MCP 工具通信入门|客户端启动子进程，用标准输入输出传 JSON-RPC 请求，服务端列出并执行工具。|工具可以运行在独立进程，双方需要约定请求和响应格式。|模型侧和工具实现可以分离，协议内容可直接观察。|这是协议子集教学实现；不能据此认定完整兼容、可靠并发或具备安全隔离。|理解 stdio 与工具发现、工具调用的关系。|直接作为面向不可信客户端的公共工具服务。|请求一个不存在的工具，观察响应 id 与错误内容是否能对应请求。
3-4|评测运行器|遍历固定题集，调用被测 Agent 和裁判，统计正确率等结果。|修改 Agent 后需要同口径检查回归。|输入、期望和得分集中，便于比较版本。|小题集不能代表真实分布；裁判错误会直接影响分数。|评测流程入门、少量回归样例。|凭几题分数做高风险选型或效果承诺。|增加一道模型容易答非所问的题，查看裁判是否只认关键词。
3-5|切块、混合检索与重排|把文档切块，用字符向量与词项分数召回，再对候选排序。|整篇检索粒度粗；只用一种匹配信号可能漏掉相关片段。|可比较切块、重叠和混合权重对候选的影响。|本地字符二元组不是预训练语义 embedding，稀疏分数也是简化实现；两种分数尺度未必可直接相加。|理解 RAG 各环节和做小数据实验。|把演示效果等同真实语义检索或生产 BM25 性能。|问一个与原文同义但措辞不同的问题，观察字符匹配的局限。
3-8|检索质量指标|计算 Recall@k、NDCG@k 和 MRR，对比命中数量和排序位置。|找到相关文档与把最相关结果排前面是不同能力。|能把“检索好不好”拆成可测指标。|需要可信相关性标注；空集合、重复结果和 k 的选择会影响比较。|检索参数和排序方法的离线比较。|没有标注数据时把指标当作真实用户满意度。|保持命中文档不变，只把相关文档往后移，观察三个指标怎样变化。
3-9|持久化与暂停恢复|生成草稿，保存状态，在人审处暂停，再带决定恢复执行。|人工不会立即回复，进程也可能重启；状态需要跨等待保留。|长流程可以分多次运行，审核决定能进入后续状态。|恢复时要避免重复副作用；本地演示不自动解决多用户隔离与并发写入。|需要等待审批的长流程原型。|未设计事务、身份与幂等却直接承载重要写操作。|在暂停后重新启动进程，检查是否读回同一份草稿并接受拒绝。
